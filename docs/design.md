## 1. Visão geral

### Produto

**Alugasim** é um produto mobile first para proprietários e pequenos empresários que administram de 4 a 10 imóveis próprios.

O produto centraliza:

- Cadastro de imóveis.
- Visualização de recebimentos.
- Envio de cobranças.
- Acompanhamento de contratos, reajustes e pendências.
- Organização da operação sem depender de planilhas, cadernos ou múltiplos aplicativos.

### Marca institucional

**CertMob** é a empresa responsável pelo produto, apresentada de forma discreta e institucional.

Hierarquia recomendada:

```text
Alugasim
por CertMob
```

A marca Alugasim deve aparecer com maior destaque no aplicativo, na landing page e nas comunicações comerciais. A CertMob aparece em documentos legais, rodapé, página institucional e materiais corporativos.

### Posicionamento

> O Alugasim torna a administração de imóveis mais prática, econômica e confiável para quem quer cuidar do próprio patrimônio sem contratar uma administradora.

### Prioridades de marca

1. Confiança.
2. Economia.
3. Praticidade.

A inovação deve aparecer principalmente na experiência simples, rápida e útil — não em uma estética tecnológica exagerada.

## 2. Direção criativa

### Ideia central

> **Controle simples para uma renda mais organizada.**

O Alugasim não deve parecer um sistema imobiliário complexo nem um aplicativo informal de classificados. A identidade precisa comunicar que o produto ajuda o proprietário a tomar conta da operação com clareza e economizar tempo e dinheiro.

### Personalidade

A marca deve ser:

- Prática.
- Segura.
- Clara.
- Econômica.
- Profissional.
- Próxima, sem ser excessivamente informal.
- Moderna, sem parecer experimental.

### Referências

A experiência pode se inspirar na clareza visual da Apple e na proximidade de produtos digitais como o Nubank, mas sem copiar elementos proprietários dessas marcas.

Absorver:

- Poucos elementos por tela.
- Hierarquia visual forte.
- Textos curtos.
- Ações principais evidentes.
- Uso cuidadoso de espaços em branco.
- Sensação de produto bem acabado.

Evitar:

- Gradientes chamativos.
- Excesso de ilustrações.
- Interfaces cheias de gráficos.
- Linguagem bancária excessivamente formal.
- Visual de imobiliária tradicional.
- Aparência de planilha corporativa.

## 3. Identidade visual

## 3.1 Logotipo do Alugasim

### Conceito

O logotipo deve combinar:

- Um “A” estilizado.
- Um elemento de imóvel ou unidade.
- Uma confirmação, organização ou recebimento.

O símbolo não precisa representar uma casa literalmente. Uma solução mais diferenciada seria criar um “A” geométrico cuja forma interna lembre:

- Uma porta aberta.
- Um check discreto.
- Um caminho ascendente.
- Um imóvel visto de forma abstrata.

A mensagem visual deve ser:

> Imóvel organizado, aluguel acompanhado e ação resolvida.

### Versões

- **Logo principal:** símbolo + palavra “Alugasim”.
- **Logo compacto:** símbolo acima ou ao lado do nome.
- **Ícone:** apenas o símbolo.
- **Versão monocromática:** para documentos e fundos com pouco contraste.
- **Versão reduzida:** para favicon, avatar e aplicativo.

### Construção

- Formas geométricas simples.
- Cantos levemente arredondados.
- Espessura consistente.
- Boa leitura em tamanhos pequenos.
- Nenhum detalhe dependente de cor.
- Área de proteção equivalente à altura do “A” ao redor do logotipo.

### Uso incorreto

Não utilizar o logotipo:

- Com sombras fortes.
- Sobre fundos com baixo contraste.
- Esticado horizontal ou verticalmente.
- Com contorno artificial.
- Com cores não previstas no sistema.
- Em combinação com ícones de chave, cifrão ou prédio sem necessidade.

## 3.2 Logotipo da CertMob

A CertMob deve ter uma assinatura visual mais discreta e neutra.

Recomendação:

- Tipografia simples.
- Símbolo reduzido ou apenas lettering.
- Uso predominante em azul profundo ou grafite.
- Sem competir visualmente com o Alugasim.

Aplicação preferencial:

```text
Alugasim
por CertMob
```

## 5. Tipografia

### Família

Usar **Inter** como fonte principal.

Alternativas:

- `system-ui`.
- `-apple-system`.
- `BlinkMacSystemFont`.
- `Segoe UI`.

### Escala tipográfica

| Nome | Tamanho | Peso | Uso |
| --- | ---: | ---: | --- |
| `display` | 32 px | 700 | Títulos de destaque |
| `heading-1` | 28 px | 700 | Títulos de página |
| `heading-2` | 22 px | 650 | Seções principais |
| `heading-3` | 18 px | 650 | Cards e blocos |
| `body-lg` | 18 px | 400 | Mensagens importantes |
| `body` | 16 px | 400 | Texto padrão |
| `body-sm` | 14 px | 400 | Apoio e metadados |
| `caption` | 12 px | 500 | Labels auxiliares |

### Regras

- Texto principal nunca deve ser menor que 16 px em fluxos importantes.
- Usar line-height entre 1.4 e 1.6 para textos corridos.
- Evitar textos longos dentro de cards.
- Valores financeiros devem ter destaque visual, mas sem ocupar toda a tela.
- Usar `font-variant-numeric: tabular-nums` em tabelas e valores.

## 6. Princípios de UI/UX

### 6.1 Utilidade antes de decoração

Cada tela deve ajudar o usuário a responder rapidamente:

- Quanto recebi?
- O que ainda está pendente?
- Qual imóvel exige atenção?
- Quem precisa ser cobrado?
- Qual ação devo executar agora?

### 6.2 Uma ação principal por tela

Cada tela deve ter uma ação primária clara.

Exemplos:

- Lista de imóveis: **Cadastrar imóvel**.
- Recebimentos: **Filtrar recebimentos** ou **Registrar pagamento**.
- Pendências: **Enviar cobrança**.
- Formulário: **Salvar imóvel**.

### 6.3 Mostrar o estado atual

Não usar apenas cores ou números soltos. Um recebimento deve exibir:

```text
Apartamento Vila Mariana
Carlos Mendes
R$ 2.450,00
Vencimento: 05/09/2026
Pendente
```

### 6.4 Reduzir carga mental

- Usar padrões conhecidos.
- Preferir linguagem comum.
- Evitar menus profundos.
- Salvar automaticamente rascunhos quando possível.
- Mostrar confirmação após ações relevantes.
- Permitir desfazer ações não destrutivas.

### 6.5 Prevenir erros

Antes de enviar uma cobrança, mostrar:

- Nome do inquilino.
- Imóvel.
- Valor.
- Data de vencimento.
- Canal de envio.
- Prévia da mensagem.

Ações destrutivas, como excluir imóvel ou contrato, exigem confirmação explícita.

## 7. Arquitetura de navegação

### Navegação mobile

Usar barra inferior com quatro áreas:

1. **Início**
2. **Imóveis**
3. **Recebimentos**
4. **Mais**

O botão de ação principal pode ser contextual e aparecer como botão flutuante ou botão destacado no cabeçalho.

### Navegação laptop

Usar menu lateral:

```text
Início
Imóveis
Recebimentos
Cobranças
Contratos
Manutenções
Documentos
Configurações
```

No MVP, os itens podem ser organizados assim:

```text
Início
Imóveis
Recebimentos
Cobranças
Mais
```

Itens ainda não disponíveis devem ser evitados ou marcados claramente como “Em breve”.

## 8. Telas do MVP

## 8.1 Tela inicial

### Objetivo

Mostrar a situação financeira e as pendências mais importantes sem exigir navegação adicional.

### Conteúdo

- Saudação breve.
- Total recebido no mês.
- Total pendente.
- Total em atraso.
- Próximos vencimentos.
- Lista de alertas.
- Atalho para cadastrar imóvel.
- Atalho para enviar cobrança.

### Exemplo

```text
Bom dia, Marcelo

Resumo de setembro

Recebido
R$ 8.450,00

Pendente
R$ 2.450,00

Em atraso
R$ 1.200,00

Ações necessárias

1 cobrança precisa ser enviada
2 recebimentos vencem nos próximos 3 dias
```

## 8.2 Lista de imóveis

### Objetivo

Permitir visualizar e gerenciar o portfólio.

Cada item deve mostrar:

- Nome ou endereço resumido.
- Inquilino atual.
- Valor do aluguel.
- Situação do recebimento.
- Próxima ação relevante.

### Ações

- Cadastrar imóvel.
- Abrir detalhes.
- Editar imóvel.
- Ver recebimentos relacionados.
- Enviar cobrança.

### Estado vazio

```text
Seus imóveis começam aqui

Cadastre o primeiro imóvel para acompanhar contratos, recebimentos e cobranças.

[ Cadastrar imóvel ]
```

## 8.3 Cadastro de imóvel

### Campos essenciais

- Nome de identificação.
- Endereço.
- Tipo de imóvel.
- Valor do aluguel.
- Dia de vencimento.
- Nome do inquilino.
- Telefone ou canal de cobrança.
- Data de início do contrato.
- Índice de reajuste.
- Observações.

### Regras de UX

- Dividir o formulário em etapas curtas no mobile.
- Informar quais campos são obrigatórios.
- Usar exemplos nos placeholders.
- Preservar dados preenchidos se o usuário sair da tela.
- Validar campos no momento adequado, sem interromper prematuramente.

### Botões

```text
[ Cancelar ] [ Salvar imóvel ]
```

## 8.4 Recebimentos

### Objetivo

Dar uma visão clara do dinheiro recebido, pendente e atrasado.

### Filtros

- Período.
- Imóvel.
- Status.
- Inquilino.

### Status

- Recebido.
- Pendente.
- Em atraso.
- Cobrança enviada.

### Exemplo de item

```text
Casa Centro
Ana Paula
R$ 1.850,00
Vence em 3 dias
Pendente
```

O status deve aparecer em texto e com ícone, nunca apenas por cor.

## 8.5 Enviar cobrança

### Fluxo

1. Selecionar recebimento pendente.
2. Conferir dados.
3. Escolher canal.
4. Revisar mensagem.
5. Enviar.
6. Exibir confirmação.

### Prévia

```text
Olá, Ana Paula.

Passando para lembrar que o aluguel do imóvel Casa Centro,
no valor de R$ 1.850,00, vence em 05/09/2026.

Qualquer dúvida, estou à disposição.
```

### Confirmação

```text
Cobrança enviada

A mensagem foi enviada para Ana Paula.
```

## 9. Componentes

### Button

Variantes:

- `primary`.
- `secondary`.
- `outline`.
- `ghost`.
- `destructive`.

Regras:

- Altura mínima de 44 px.
- Texto específico para a ação.
- Estado de carregamento.
- Estado desabilitado acessível.
- Ícone somente quando ajudar na compreensão.

```tsx
<Button variant="primary">
  Cadastrar imóvel
</Button>
```

### StatusBadge

Nunca depender apenas da cor.

```tsx
<StatusBadge status="pending">
  Pendente
</StatusBadge>
```

Mapeamento:

```ts
const statusVariants = {
  received: "success",
  pending: "warning",
  overdue: "danger",
  sent: "info",
};
```

### PropertyCard

Deve apresentar:

- Identificação do imóvel.
- Inquilino.
- Valor.
- Situação.
- Ação principal.

### FinancialSummaryCard

Usar para:

- Recebido.
- Pendente.
- Em atraso.

Cada card deve incluir:

- Rótulo.
- Valor.
- Período.
- Ícone.
- Texto auxiliar quando necessário.

### EmptyState

Todo estado vazio deve explicar:

1. O que está vazio.
2. Por que isso importa.
3. O que o usuário pode fazer.

### ConfirmationDialog

Usar para:

- Excluir imóvel.
- Excluir contrato.
- Alterar manualmente valor de reajuste.
- Cancelar cobrança já preparada.
- Remover documento.

## 10. Acessibilidade

### Requisitos

- Contraste mínimo compatível com WCAG AA.
- Navegação completa por teclado em laptop.
- Foco visível em todos os controles.
- Labels associados aos campos.
- Mensagens de erro próximas ao campo correspondente.
- Não usar apenas cor para indicar status.
- Áreas de toque de no mínimo 44 × 44 px.
- Ícones com `aria-label` quando não acompanhados de texto.
- Modais com foco controlado.
- Leitura adequada por leitores de tela.
- Respeitar configurações de aumento de fonte.
- Não usar animações essenciais para compreender o fluxo.

### Exemplo acessível

Inadequado:

```text
[bolinha vermelha]
```

Adequado:

```text
[ícone de alerta] Pagamento em atraso
```

## 11. Tom de voz

### Características

- Claro.
- Direto.
- Respeitoso.
- Útil.
- Tranquilo.
- Sem linguagem jurídica desnecessária.
- Sem infantilização do usuário.

### Exemplos

| Situação | Texto recomendado |
| --- | --- |
| Sucesso | Imóvel cadastrado com sucesso. |
| Recebimento | Pagamento registrado. |
| Pendente | Este aluguel ainda está pendente. |
| Atraso | Este pagamento está 3 dias atrasado. |
| Cobrança | Cobrança pronta para envio. |
| Falha | Não foi possível enviar a cobrança. Tente novamente. |
| Campo obrigatório | Informe o valor do aluguel. |
| Exclusão | Excluir este imóvel? Essa ação não poderá ser desfeita. |

### Evitar

- “Ops, parece que algo deu errado” sem explicar o problema.
- “Você precisa fazer isso agora” em tom agressivo.
- Termos técnicos sem contexto.
- Excesso de exclamações.
- Promessas absolutas como “nunca mais perca dinheiro”.

## 13. Regras para React e Tailwind

### Organização

Separar:

- `components/ui`: componentes genéricos.
- `components/domain`: componentes de imóveis, recebimentos e cobranças.
- `features/properties`: fluxo de imóveis.
- `features/payments`: fluxo de recebimentos.
- `features/collections`: fluxo de cobranças.
- `lib`: utilitários.
- `styles`: tokens e estilos globais.

### Componentes

Preferir componentes reutilizáveis:

```text
Button
Input
Select
Dialog
StatusBadge
PropertyCard
PaymentCard
SummaryCard
EmptyState
LoadingState
```

### Variantes

Usar `cva` para estados e variantes:

```tsx
const statusBadgeVariants = cva(
  "inline-flex items-center gap-1 rounded-full px-3 py-1 text-sm font-medium",
  {
    variants: {
      status: {
        received: "bg-success-100 text-success-700",
        pending: "bg-warning-100 text-warning-700",
        overdue: "bg-danger-100 text-danger-700",
        sent: "bg-brand-100 text-brand-800",
      },
    },
  }
);
```

### Responsividade

A prioridade deve ser:

1. Mobile pequeno.
2. Mobile grande.
3. Tablet.
4. Laptop.
5. Desktop amplo.

Usar layout fluido antes de criar breakpoints específicos.

```tsx
<div className="grid grid-cols-1 gap-4 md:grid-cols-2 xl:grid-cols-3">
  {properties.map((property) => (
    <PropertyCard key={property.id} property={property} />
  ))}
</div>
```

### Regras de implementação

- Não usar ternários extensos para estados visuais.
- Não criar cores isoladas fora dos tokens.
- Não esconder ações importantes apenas em menus de três pontos.
- Não usar tabelas complexas como solução principal no mobile.
- Não criar uma tela diferente para cada pequena variação de estado.
- Manter lógica de negócio separada da apresentação.
- Usar componentes com nomes orientados ao domínio do produto.

## 14. Critérios de sucesso

A primeira versão do design estará adequada quando o usuário conseguir:

- Cadastrar um imóvel sem ajuda externa.
- Identificar rapidamente quanto recebeu no mês.
- Encontrar pagamentos pendentes ou atrasados.
- Enviar uma cobrança em poucos passos.
- Entender o status de cada aluguel sem depender de cores.
- Usar o sistema confortavelmente no celular.
- Reconhecer o Alugasim como uma ferramenta prática, confiável e econômica.

```text
Marca principal: Alugasim
Marca institucional: CertMob
Personalidade: prática, confiável e econômica
Estilo: sóbrio-amigável
Referências: clareza da Apple e proximidade de produtos digitais
```
